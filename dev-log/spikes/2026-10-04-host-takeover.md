# Spike：主機交接（請求接任、不同意、強制接任）實網驗證

- **日期**：2026-10-04
- **狀態**：🟢 通過（4 種情境），附已知限制
- **程式**：`dev-log/spikes/session-spike.html`（`js/net/session.js` + `js/net/transport-peer.js`，由 `window.T` 驅動；狀態紀錄加上世代 `g`、主機與待決請求 `ho`）

## 1. 要驗證的假設

1. 成員請求接任，主機 10 秒內沒按不同意：房間移到下一世代，請求者當主機，其他分頁跟上，遊戲狀態不變。
2. 主機按不同意：請求者收到 `err.handoverDeclined`，房間不動，強制計時器不誤觸。
3. 主機卡死（JS 停住、ID 仍被佔住）：請求者在另一個 ID 強制開房，其他分頁跟上；舊主機甦醒後讓位並加入新房。
4. 主機按同意：立即交接。

## 2. 成功標準（事前訂定）

- [x] 情境 1：約 10 秒後交接，三分頁全部上線、同一主機、同一世代，位置／現金／logSeq／階段不變，無錯誤
- [x] 情境 2：請求者收到不同意，等 14 秒仍非主機、世代不變
- [x] 情境 3：請求者 30 秒內接任並收到 `err.hostSilent`，第三分頁跟上；舊主機甦醒後成為一般成員，三分頁遊戲狀態一致
- [x] 情境 4：按同意後數秒內交接完成

## 3. 環境

Windows 11、Claude 內建瀏覽器（Chromium）、同一台機器 3 個分頁（A、B、C）、peerjs@1.5.5、0.peerjs.com 公用信令、本機 `python -m http.server 5173`、`?room=ho1004a`。正式時序（`SESSION_TIMING`、`HOST_TIMING`）：交接等待 10 秒、強制寬限 3 秒、心跳逾時 10 秒、移房延遲 1.5 秒。

## 4. 執行紀錄

時間取自各分頁 `performance.now()`。同一分頁內的間隔是精確值；跨分頁對齊用牆鐘換算，誤差約 0.5 秒內。

### 情境 1：B 請求接任，主機 A 不回應

| 事件 | 時間（請求起算） |
|------|------|
| 三分頁看到待決請求 | 0.2 s 內 |
| 房間移到世代 1（B 收到 move） | 10.2 s |
| B 在新 ID 開房 | 11.2 s |
| C 加入 B | 收到 move 後 3.0 s |
| 舊主機 A 退位並加入 B | 收到 move 後 1.5 s 退位、3.7 s 上線 |

交接前後：位置 `[6,0,0]`、現金 `[1500,1500,1500]`、`logSeq 3`、階段 `buy`、輪到 0 號，全部相同；三分頁錯誤清單皆空，三個座位都在線。

### 情境 2：C 請求接任，主機 B 按不同意

請求 2 秒後主機端顯示剩 7,991 ms；B 送出不同意後 0.5 秒內請求清除。C 收到 `err.handoverDeclined`；請求後 14 秒 C 仍非主機、世代仍為 1、主機仍是 B（強制計時器 13 秒未觸發）。

### 情境 3：主機 B 卡死 45 秒（busy loop），C 在卡死 1.6 秒後請求接任

| 時間（卡死起算） | 事件 |
|------|------|
| 1.6 s | C 送出請求（B 卡住，收不到） |
| 8.9 s、9.3 s | C、A 心跳逾時，進入重連 |
| 9 到 25 s | 重連：B 的 ID 仍被佔住，撥 B 的 ID 10 秒逾時 |
| 25.1 s | C 強制在世代 2 的 ID 開房，收到 `err.hostSilent` |
| 34.8 s | A 在下一輪重試加入 C |
| 45.1 s | B 甦醒：房間收到 A、C 的斷線；B 自己的迴路也逾時，退位 |
| 46.3 s | B 重新取得自己的 ID，開房時探測另一個 ID，找到 C，讓位 |
| 50.4 s | B 加入 C（甦醒後 5.3 秒），三個座位都在線 |

結束時三分頁：世代 2、主機 C、位置 `[6,6,10]`、現金 `[1500,1400,1500]`、`logSeq 17`、階段 `postRoll`，完全一致。測試期間數分鐘無人操作，遊戲由逾時與電腦代打推進（log 有 `log.timeout`、`log.botOff`），不是資料遺失。

### 情境 4：A 請求接任，主機 C 約 1.5 秒後按同意

以 A 看到待決請求為起點：3.0 s 房間移到世代 3，4.1 s A 開房，5.9 s 與 6.8 s 另兩個分頁加入。三個座位都在線，無錯誤。

## 5. 結論

四個假設都通過。

1. 主機在線時交接約 11 秒（10 秒等待 + 約 1 秒取得新 ID），其他分頁在移房後 3 到 4 秒跟上。
2. 主機卡死時約 25 秒由請求者接任，另一分頁約 35 秒跟上；比只靠信令伺服器釋放 ID（約 100 秒，見 `2026-10-04-session-real-network.md`）快約 4 倍。
3. 舊主機甦醒後自動讓位，未出現兩個房間並存。

**設計變更（本 spike 前的單元測試已發現）**：主機原本只在「成員靜默逾時」時探測另一個 ID；卡死的主機甦醒時先收到的是成員的斷線事件，不會觸發探測，會一直獨自開房。已改為任何成員連線結束都探測（`host-room.js` 的 `leave()` 呼叫 `onDrop`），並加上單元測試。實網中 B 甦醒時同時發生迴路逾時，由「開房時探測」路徑讓位，兩條路徑都有覆蓋。

## 6. 限制

1. 三分頁同機，WebRTC 走本機迴路；跨網路與手機背景凍結未測（GAPS G2）。
2. 卡死以 busy loop 模擬；真實的分頁凍結（行動裝置切背景）可能讓計時器被節流，不等於完全停止。
3. 強制接任的 25 秒中，10 秒是撥號到卡死主機 ID 的逾時，取決於 PeerJS 與信令伺服器行為；樣本數 1。
4. 情境 3 中舊主機甦醒時曾短暫（約 3 秒）重新持有自己的舊 ID；這段時間新加入者會先連到它，再被轉到新房。

## 7. 過期條件

peerjs 升級、改用自架 PeerServer、或調整 `SESSION_TIMING` / `HOST_TIMING` 的交接與逾時參數時重測。
